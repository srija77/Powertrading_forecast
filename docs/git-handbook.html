1. Installing Git and configuring it once

Install Git, then set four config values — identity, default branch, line endings, credentials. Git refuses to commit without a name and email, so this is not optional setup.

PlatformInstall commandNotes
Windowswinget install --id Git.Git -e --source wingetBundles Git Bash and Git GUI; the installer from git-scm.com works too
macOSbrew install gitOr xcode-select --install for Apple’s older bundled build
Ubuntu / Debiansudo apt update && sudo apt install git
Fedora / RHELsudo dnf install git

Confirm it landed and which build you got:

git --version

The one-time configuration

Run these once per machine. --global writes to ~/.gitconfig; drop the flag inside a repo to override a value for that repo alone.

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global core.autocrlf true          # Windows only: LF in the repo, CRLF in your working tree
git config --global credential.helper manager   # Windows: stores GitHub creds in Credential Manager
git config --global pull.rebase false           # make git pull merge rather than warn about ambiguity

The email you set here is what GitHub matches commits against — use the address on your GitHub account or your commits will not link to your profile.

Reading your config back

git config --list --show-origin   # every value and the file it came from
git config user.email             # one value, as Git resolves it here
git config --global --edit        # open ~/.gitconfig in your editor

--show-origin is the one to reach for when a value is not what you expect: it reveals whether a repo-local or system config is shadowing your global setting.

2. Starting a repository

There are two entry points: git init turns a folder you already have into a repository, and git clone copies one that already exists. Pick one — doing both to the same project is what creates unrelated histories.

Path A: a folder you already have

cd my-project
git init                      # creates .git/ -- the whole repository lives in that one folder
git add .
git commit -m "Initial project structure"

Then create an empty repository on GitHub — no README, no .gitignore, no licence — and attach it:

git remote add origin https://github.com/you/my-project.git
git push -u origin main       # -u sets the upstream so later git push needs no arguments

If GitHub added a README for you, that repo already has its own root commit and git pull will refuse to merge — see common errors.

Path B: a repository that already exists

git clone https://github.com/you/my-project.git
cd my-project

clone does init, remote add origin, fetch and checkout in one step, and sets up upstream tracking. Nothing else is needed.

Inspecting the remote wiring

git remote -v                     # the URLs behind each remote name
git remote show origin            # branches, tracking, and what push/pull would do
git remote set-url origin <url>   # change where origin points
git remote rename origin upstream
git remote remove origin

.gitignore

Add this before your first commit — anything already committed keeps being tracked even after you ignore it.

.venv/
__pycache__/
*.pyc
.env
.DS_Store

Already committed something you meant to ignore? git rm --cached <path> untracks it without deleting the file, then commit.

3. The everyday loop

Git keeps your work in four places, and the commands you use daily just move changes between them. git commit snapshots the staging area, never your files directly — that is the whole reason git add exists.

Read down the right for the forward path, up the left to undo. git pull is absent because it is two of these steps at once: a git fetch followed by a git merge.

Status and staging

git status              # what changed, what is staged, what branch you are on
git status --short      # compact: M = modified, A = added, D = deleted, ?? = untracked

git add path/to/file    # stage one file
git add .               # stage everything under the current directory
git add -p              # stage hunk by hunk, answering y/n -- the best habit for clean commits
git rm --cached <path>  # unstage and untrack, keeping the file on disk

The left column of git status --short is the staging area, the right column is your working tree.  M means modified but not staged; M  means staged; MM means staged, then modified again.

Committing

git commit -m "Add price forecast baseline"
git commit -am "..."           # stage all *tracked* modifications and commit -- skips new files
git commit --amend             # rewrite the last commit (message or contents)
git commit --amend --no-edit   # fold staged changes into the last commit, same message

Never --amend a commit you have already pushed and someone else has pulled — it rewrites history and their next pull will conflict.

Reading history

git log --oneline --graph --decorate --all   # the one to memorise: every branch, one line each
git log -5                                  # the last five commits in full
git log --stat                              # which files each commit touched
git log -p <path>                           # the full diff of every commit touching one file
git log --since="2 weeks ago" --author="Srija"

4. Branching and merging

A branch is a movable pointer to one commit — nothing is copied when you create one, which is why branching is instant and cheap.

git branch                      # list local branches, * marks the current one
git branch -a                   # include remote-tracking branches
git branch -vv                  # show each upstream and how far ahead/behind

git switch -c feature/forecast  # create a branch and move to it
git switch main                 # move to an existing branch
git switch -                    # back to the branch you were just on

git checkout still does both jobs, but git switch (branches) and git restore (files) were split out in Git 2.23 precisely because checkout doing both was the most common source of accidents. Prefer the new pair.

Merging

git switch main
git merge feature/forecast
git branch -d feature/forecast   # -d refuses if unmerged; -D forces

Two outcomes are possible, and which one you get is not a choice you make:

SituationWhat Git doesResult in the log
main has no new commits since the branch startedFast-forward: just moves the main pointer forwardA straight line, no merge commit
Both branches have new commitsThree-way merge: builds a new commit with two parentsA fork that rejoins
Both changed the same linesStops with a conflict for you to resolveA merge commit once you finish

Force the shapes when you care: --no-ff always makes a merge commit (keeps the branch visible in history), --ff-only refuses unless it can fast-forward (keeps history linear).

Resolving a conflict

git status                # lists every file under "Unmerged paths"
# edit each file, delete the <<<<<<< ======= >>>>>>> markers
git add <resolved-file>   # staging a conflicted file marks it resolved
git commit                # completes the merge, pre-filled message

git merge --abort         # bail out entirely, back to before the merge

git diff --name-only --diff-filter=U lists just the still-conflicted files — useful mid-merge in a large repo.

5. Working with remotes

git fetch is always safe — it downloads commits and updates origin/main without touching your files. git pull is fetch plus a merge into your current branch, so it is the one that can produce conflicts.

git fetch origin              # download; your working tree is untouched
git fetch --all --prune       # all remotes, and delete stale origin/* refs
git log --oneline HEAD..origin/main   # what you are about to pull in
git diff HEAD origin/main     # the actual changes it would bring
git pull                      # fetch + merge, once you are happy

That fetch → log HEAD..origin/main → pull sequence is the habit that stops surprise merges.

Pushing and upstream tracking

git push                          # once upstream is set
git push -u origin main           # first push: sets upstream for later pushes
git push origin feature/forecast  # push a branch without setting upstream
git push --force-with-lease       # rewrite remote history, abort if someone else pushed
git push origin --delete old-branch

Use --force-with-lease, never bare --force. Both rewrite the remote branch, but --force-with-lease checks that the remote is still where you last saw it and refuses if a colleague pushed in between — bare --force silently destroys their commits.

Remote-tracking branches

origin/main is a local, read-only bookmark recording where main was on the server at your last fetch. It does not update on its own, which is why git status can claim you are up to date when the server has moved on — it is comparing against a possibly stale origin/main.

git branch -vv                             # local branches, upstreams, ahead/behind counts
git rev-list --left-right --count main...origin/main   # "3  2" = 3 local-only, 2 remote-only
git branch --set-upstream-to=origin/main main          # attach a branch to a remote one

6. Undoing things safely

Pick by what you want to undo, not by which command you half-remember. Only two entries here can lose work: restore and reset --hard.

What you want to undoCommandLoses work?
Edits to a file, not yet stagedgit restore <path>Yes — gone for good
Every uncommitted edit in the treegit restore .Yes
A staged file, keeping the editsgit restore --staged <path>No
The last commit, keeping changes stagedgit reset --soft HEAD~1No
The last commit, keeping changes unstagedgit reset HEAD~1No
The last commit and its changes entirelygit reset --hard HEAD~1Yes
A commit that is already pushedgit revert <sha>No — adds an inverse commit
Just the last commit’s messagegit commit --amendNo
Nothing — set work aside for latergit stashNo

The three modes of reset

All three move the branch pointer; they differ only in how much they drag with it:

  • --soft — moves the pointer. Staging area and files untouched, so the commit’s changes sit staged, ready to recommit.
  • --mixed (the default) — moves the pointer and clears the staging area. Your files keep every change.
  • --hard — moves the pointer, clears staging, and overwrites your files. This is the only destructive one.

revert vs reset

Use revert for anything already pushed. It does not delete the bad commit; it adds a new commit that undoes it, so the history everyone else already pulled stays valid. reset rewrites history and is only safe on commits that never left your machine.

git revert <sha>           # one commit
git revert <old>..<new>    # a range
git revert -n <sha>        # stage the reversal without committing yet

Stashing

git stash push -m "half-done forecast tweak"
git stash list                  # stash@{0} is the most recent
git stash show -p stash@{0}     # what is in it
git stash pop                   # re-apply the newest and drop it
git stash apply stash@{1}       # re-apply an older one, keep it in the list
git stash push -u               # include untracked files -- skipped by default
git stash drop stash@{0}

git stash push -u matters more than it looks: without -u, brand-new files stay in your working tree and follow you onto whatever branch you switch to.

7. Debugging and inspecting

When Git behaves unexpectedly, the fix is almost always to find out what state the repository is actually in rather than to try another command. Everything below is read-only and safe to run at any time.

What changed

git diff                      # working tree vs staging area -- what is NOT staged
git diff --staged             # staging area vs last commit -- what IS staged
git diff HEAD                 # everything uncommitted, staged or not
git diff main..feature        # the tip-to-tip difference between two branches
git diff --stat               # just filenames and +/- line counts
git diff --name-only          # filenames alone, good for piping
git diff --check              # flag whitespace errors before committing

What is in a commit, tree or branch

git show <sha>                # message + full diff of one commit
git show <sha>:path/to/file   # that file as of that commit
git show --stat <sha>         # which files it touched, no diff
git ls-tree -r --name-only HEAD   # every tracked file at a commit
git ls-files                  # every file in the staging area
git cat-file -p <sha>         # the raw object: commit, tree or blob

Who and when

git blame path/to/file        # last commit to touch each line
git blame -L 40,60 <path>     # only lines 40-60
git log -S "def forecast"     # commits that added or removed that string
git log -G "regex"            # same, but a regex over the diff
git log --follow <path>       # history across renames
git shortlog -sn              # commit counts per author

git log -S is the one most people never learn and then use constantly: it answers “when did this line of code appear?” directly.

The state of the repository itself

git status --short --branch   # compact status plus ahead/behind
git rev-parse HEAD            # the full sha HEAD points to
git rev-parse --abbrev-ref HEAD      # the current branch name
git rev-list --count HEAD     # how many commits are in this history
git rev-list --max-parents=0 --all   # every ROOT commit
git merge-base main feature   # the commit two branches diverged from
git fsck                      # check object integrity, list dangling objects
git count-objects -vH         # repository size on disk

That rev-list --max-parents=0 --all line is the direct test for the “unrelated histories” error: two hashes back means two independent history trees.

The reflog — your safety net

Every move of HEAD is logged locally for 90 days, including the ones that “lost” commits. A bad reset --hard, a deleted branch, a botched rebase: all recoverable from here.

git reflog                    # every position HEAD has held, newest first
git reflog show main          # just one branch of movements
git reset --hard HEAD@{2}     # jump back to where you were two moves ago
git switch -c rescue <sha>    # resurrect a lost commit onto a new branch

Finding the commit that broke something

git bisect start
git bisect bad                # the current commit is broken
git bisect good <old-sha>     # this one worked
# Git checks out the midpoint; test, then mark it good or bad
git bisect reset              # done -- back to where you started

git bisect run pytest -q      # or automate it: Git finds the culprit unattended

Bisect is a binary search, so it finds the guilty commit in about log₂(n) tests — ten steps across a thousand commits.

8. Common errors decoded

fatal: refusing to merge unrelated histories

The local repo and the remote were started separately, so they share no common ancestor and Git cannot compute a merge base. Confirm it:

git rev-list --max-parents=0 --all   # two hashes = two independent histories

This happens when you create the repo on GitHub with a README and also run git init locally, then connect them. Two fixes:

# The remote holds nothing you need (a stub README) -- replace it with your history:
git push -u origin main --force-with-lease

# You want both histories joined -- expect a conflict in README.md:
git pull origin main --allow-unrelated-histories

Avoid it next time by creating the GitHub repo empty, or by cloning it instead of running git init.

! [rejected] ... (non-fast-forward)

The remote has commits you do not. Git refuses to push because that would discard them. Fetch and integrate first:

git fetch origin
git log --oneline HEAD..origin/main   # see what you are missing
git pull                              # or: git rebase origin/main
git push

Only reach for --force-with-lease if you genuinely intend to overwrite the remote branch.

You are in 'detached HEAD' state

HEAD points at a commit instead of a branch — usually after git checkout <sha> or a tag. Commits you make here belong to no branch and become unreachable when you leave.

git switch -c my-branch   # keep the work: attach a branch to it
git switch main           # discard it and go back

Already left and lost a commit? git reflog still lists it.

error: Your local changes would be overwritten by merge

A pull wants to touch files you have edited. Commit them, or set them aside:

git stash push -u
git pull
git stash pop

warning: LF will be replaced by CRLF

A Windows line-ending notice, not an error. It means Git will normalise the file. Setting core.autocrlf true plus a .gitattributes with * text=auto silences it and keeps the repo consistent across machines.

fatal: Authentication failed

GitHub stopped accepting account passwords over HTTPS in 2021. Use a personal access token as the password, or switch to SSH:

git remote set-url origin git@github.com:you/repo.git
ssh -T git@github.com    # verify the key works

On Windows, git config --global credential.helper manager stores the token in Credential Manager so you enter it once.

fatal: not a git repository

You are outside a repository, or above the folder holding .git/. Check where Git thinks it is:

git rev-parse --show-toplevel   # the repository root, or an error if there is none

Nothing works and you want the truth

Run the three lines that describe the whole situation with no interpretation:

git status --short --branch
git log --oneline --graph --decorate --all -20
git remote -v
